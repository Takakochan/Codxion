--------------------------------
1. 構造体（struct）の基本
--------------------------------

このプロジェクトでは4つの構造体を作った。

  t_parameter … コマンドライン引数から作る設定値（人数、各種タイムアウト、
                スケジューラ種別など）。1シミュレーションにつき1個だけ存在する。

  t_dongle    … 共有資源（USBドングル）。ID・使用開始時刻・mutex・
                条件変数（cond）を持つ。N個ぶん配列で確保する。

  t_coder     … スレッドの主役。左右のdongleへのポインタ（left_hand/
                right_hand）とパラメータを持つ。同じくN個ぶん配列で確保する。

  t_session   … 上記3つ（と将来追加するもの）をまとめて持つ「共有状態
                一式」の入れ物。init_param() が組み立てて、mainが
                各スレッドにポインタで配る。

【やさしい用語解説】
  構造体（struct）：複数の値を1つの名前でまとめて持ち運べる「箱」。
    Pythonでいうクラス／dataclassに近い。
  typedef：長い型名（struct s_dongle）に短い別名（t_dongle）を
    付ける仕組み。書く手間を減らすだけで、動作には影響しない。
  指示付き初期化子（designated initializer）：
    t_parameter param = { .number_of_coders = 5, ... };
    のように「フィールド名を指定して」値を詰める書き方。C99からの機能。
    Pythonのキーワード引数に近い書き味。


--------------------------------
2. なぜ構造体が「必須」なのか
--------------------------------

  ・t_coder が必須な理由：
    pthread_create に渡せる引数は void *arg 1個だけ。
    coderが必要とする複数の値（自分のID、左右のdongle等）を渡すには、
    1個のポインタにまとめる＝構造体にするしかない。
    しかもこの課題は「グローバル変数禁止」なので、グローバル配列で
    共有することもできない。

  ・t_dongle が必須な理由：
    各dongleは独立して取り合われる資源なので、dongleごとに別々の
    mutex/condが要る。パラレル配列（locks[n], conds[n], in_use[n]）
    でもできなくはないが、インデックスがズレるとバグる。構造体にして
    1個のポインタでmutex・cond・状態全部にアクセスできるようにする方が安全。

  ・t_parameter は「必須」ではなく「強く推奨」：
    引数を1つずつバラで8個渡すのは順序ミスの温床（time_to_debug と
    time_to_refactor を入れ替えて渡してもコンパイラは気づかない）。
    構造体1個・ポインタ1個にまとめれば順序ミスが起きようがない。

  ・t_session が生まれた理由：
    pthread_create の「引数1個」制約は、スレッドが増えるほど・
    共有したい情報が増えるほど効いてくる。終了フラグ、ログ用mutex、
    開始時刻など後から増える共有情報をまとめて持つ場所が必要になる。
    out引数（&dongles, &coders のような形）で個別に返す案も検討したが、
    共有フィールドが増えるたびに全関数のシグネチャを直す必要が出るため、
    「1つの構造体にまとめて返す」方を採用した。


--------------------------------
3. 初期化（初期化）と代入（代入）の違い
--------------------------------

  ・初期化：変数が生まれるその場で値を与えること。
      t_parameter param = { .field = val, ... };  ← これは初期化
  ・代入：すでにある変数に後から値を書き込むこと。
      dongles[i].dongle_id = i;  ← malloc後に書いているので「代入」

  malloc() が返すメモリは中身が未初期化（ゴミ値）。なので
  malloc直後にいきなりフィールドを読むと危険。全フィールドに
  代入し終えた瞬間、その要素は実質的に「初期化済み」とみなせる。

  pthread_mutex_t / pthread_cond_t だけは特別：
  これらはopaque型（中身を直接いじれない型）なので、= で代入しても
  正しく初期化したことにならない。pthread_mutex_init() /
  pthread_cond_init() を呼ぶ、または静的初期化子
  （PTHREAD_MUTEX_INITIALIZER）を使うことが唯一正しい初期化方法。


--------------------------------
4. . と -> の使い分け
--------------------------------

  ルールは「入れ子かどうか」ではなく「左側がポインタか値か」。

    左側が構造体そのもの（値）      → .
    左側が構造体へのポインタ        → ->  （ (*ptr).member の省略形）

  例（t_coder より）：
    t_dongle *left_hand;    // ポインタ
    t_parameter parameter;  // 値

    coder.parameter.time_to_compile   // parameter は値 → . を連続
    coder.left_hand->dongle_id        // left_hand はポインタ → ->

  チェーンの各段階で、その時点の変数がポインタか値かを見て選ぶだけでよい。


--------------------------------
5. スレッド関数とpthread_create
--------------------------------

  スレッド関数は必ずこの形でなければいけない：
    void *routine(void *arg);

  pthread_create(&thread, NULL, routine, &coders[i]);
  と呼ぶと、routine が呼び出し元とは別に「並行して」動き始める。
  実行順は保証されない（OSが自由にスケジューリングする）。

  重要：新しいスレッドは元のスレッドと同じヒープメモリを共有する。
  なので mallocで確保したdongle構造体は、全coderスレッドが
  同じアドレスを指すポインタを持つことになる＝同時に読み書きされうる。

【やさしい用語解説】
  スレッド（thread）：1つのプログラムの中で並行に動く「実行の流れ」。
  ブロックする：処理がそこで止まって、条件が整うまで先に進まないこと。


--------------------------------
6. レースコンディション・mutex・条件変数
--------------------------------

  何も保護せずに書くと危険な例：

    if (dongle->in_use == 0)   // (A) チェック
    {
        dongle->in_use = 1;    // (B) 確保
    }

  coder1が(A)を実行した直後にCPUがcoder2に切り替わり、coder2も
  「空いてる」と判断してしまう可能性がある → 両方が確保したと
  思い込む。これが「レースコンディション」。

  mutex（排他ロック）で解決：
    pthread_mutex_lock(&dongle->lock);
    if (dongle->in_use == 0) { dongle->in_use = 1; }
    pthread_mutex_unlock(&dongle->lock);
  「このブロックに入れるのは同時に1人だけ」を保証する。

  条件変数（cond）で「空くまで待つ」を効率的に：
    pthread_mutex_lock(&dongle->lock);
    while (dongle->in_use)
        pthread_cond_wait(&dongle->cond, &dongle->lock);
    dongle->in_use = 1;
    pthread_mutex_unlock(&dongle->lock);

  pthread_cond_wait は「lockを手放して眠る」→「signal/broadcastされたら
  自動的にlockを取り直してから戻る」という動き。手放すのと眠るのが
  アトミック（不可分）に行われるのがポイント（でないと通知を
  取りこぼすレースが別に起きる）。

  必ずwhileループで再チェックする理由（spurious wakeup対策）：
  1回起こされても、本当に条件を満たしたとは限らない
  （他のスレッドに先に取られている可能性がある）ため。

  返す側：
    pthread_mutex_lock(&dongle->lock);
    dongle->in_use = 0;
    pthread_cond_broadcast(&dongle->cond);
    pthread_mutex_unlock(&dongle->lock);
  broadcastは「待っている全員」を起こす。signalは1人だけ。

【やさしい用語解説】
  排他制御（mutex, mutual exclusion）：同時に1つのスレッドしか
    ある処理に入れないようにする仕組み。「鍵」に例えられる。
  レースコンディション：複数スレッドが同じデータに同時にアクセスして
    結果が実行タイミング次第で変わってしまう不具合。
  ビジーウェイト：条件が整うまで何度もループで確認し続け、
    CPUを無駄に消費すること。condはこれを避けるための仕組み。
  デッドロック：複数スレッドが互いに相手の持つ資源を待ち続けて
    誰も先に進めなくなる状態。

7. 食事する哲学者の問題（Dining Philosophers Problem）
--------------------------------

  このプロジェクトは、1965年にDijkstraが提示した古典的な問題
  「食事する哲学者の問題」の構造をそのまま流用している
  （哲学者→coder、フォーク→dongle）。

  仕様（PDFで確認済み）：
    "There is one dongle between each pair of coders. Each coder
    has a dongle on their left side and a dongle on their right side."
  → dongleの数はcoderの数と同じで、各coderの左右に固定で1個ずつ
    隣接する。これは設計の自由選択ではなく課題の必須要件。

  この配置（N個の要素が輪になり、隣同士だけが繋がる）は
  一般に「リング・トポロジー（ring topology）」と呼ばれる。
  実装は普通の配列＋剰余（% N）でよく、リンクリストにする必要はない：

    coders[i].left_hand  = &dongles[i];
    coders[i].right_hand = &dongles[(i + 1) % N];

  一度セットしたら、あとはポインタを直接辿るだけ（O(1)）。
  トポロジーは実行中に変化しないので、リンクリストの強み
  （挿入・削除のしやすさ）を活かせる場面がそもそもない。

  「dongleをプールにして早い者勝ちにした方が速いのでは？」
  という疑問について：compile中でない時間（debug/refactor）は
  そもだそもdongleを一切必要としないフェーズなので、「暇な人を
  待たせない」問題はフェーズ分割によってすでに解決されている。
  リング構造が担うのは「隣り合う2人が同じdongleを取り合うときの
  公平な調停」という別の問題。

  リング状にすると必然的に「循環待ち（circular wait）」が起きる
  ——これはデッドロックが成立する4条件（Coffmanの4条件）の1つ。
  この課題が fifo/edf スケジューラと dongle_cooldown を要求している
  のは、まさにこの循環待ちにどう対処するかを実装させるため。

  （参考・先の学習用）循環待ちへの有名な対処法：
    ・resource hierarchy solution：資源に番号をつけ、常に番号の
      小さい方から先に取るルールにすると循環待ちが構造的に起きない
    ・arbitrator / waiter solution：同時に着席できる人数を
      N-1人までに制限する管理役を置く

【やさしい用語解説】
  循環待ち（circular wait）：A がBの資源を待ち、BがCの資源を待ち…
    と輪になって、誰も先に進めなくなる状態。
  スケジューラ（この課題での意味）：複数のcoderが同じdongleを
    欲しがったとき、誰に渡すかを決めるルール（fifo=先着順、
    edf=締め切りが近い人優先）。


--------------------------------
8. ログ仕様まわりで気づいたこと
--------------------------------

  ・ログに登場するのは「コーダー番号」だけ（dongleの番号は出力に
    一切登場しない）。なので dongle_id は連番である必要はなく、
    完全に内部用のラベルでよい。

  ・PDFに "Coder number 1 sits next to coder number
    number_of_coders" とあり、コーダー番号は1始まりを示唆している。
    今の init_coders() は coders[i].coder_id = i; と0始まりなので、
    ログ出力時にズレないよう、どこかで +1 する必要がありそう
    （coder.c を書く段階で要注意）。

  ・ログ関連の許可関数：
    write() … libcのバッファリングを経由しない低レベル出力。
      burnoutメッセージのように「10ms以内に確実に表示」が
      要求される箇所で使う想定。
    usleep() … 監視スレッドがビジーループでCPUを無駄にしないよう、
      チェックの合間に短時間眠らせる（例: usleep(1000) で1ms）。
    gettimeofday() … シミュレーション開始からの経過ミリ秒
      （timestamp_in_ms）を計算するのに使う。


--------------------------------
9. ビルド・テストで学んだこと
--------------------------------

  ・-Wall -Wextra -Werror が付いていると、ただの警告（未使用変数など）
    もビルドエラーとして扱われる。ロジックのバグとは別物として区別する。

  ・Makefile の SRCS に書かれていないファイル（init.c, dongle.c,
    coder.c など）は、make を実行しても一切コンパイル対象に
    入らない。「動いているはず」と「ビルド対象に入っている」は別。

  ・init_param() のような「値を返す関数」を作るときは、ヘッダの
    プロトタイプ宣言と .c 側の実際の定義（特に返り値の型）を
    必ず一致させる必要がある。ズレていると "conflicting types" で
    コンパイルエラーになる。

10. 次にやること（ロードマップ）
--------------------------------

  0. Makefile の SRCS に init.c/dongle.c/coder.c を追加し、
     main.c で session を実際に使ってビルドを通す
  1. init.c でリング状トポロジーの配線（left_hand/right_hand）を組む
  2. utils.c：タイムスタンプ取得・ログ出力用mutexなど共通処理
  3. dongle.c：mutex+condによるdongleの取得・返却ロジック
  4. coder.c：coder_routine()（compile→debug→refactorのループ）
     ※ t_coder に pthread_t thread と compiles_done を追加する必要あり
  5. eye.c：monitorスレッド（burnout検知・終了判定）
  6. FIFO/EDF用の自前ヒープ（t_heap/t_request）※課題の必須要件
  7. main.c の仕上げ（生成→join→mutex/cond destroy→free）

  依存の向き： 0 → 1 → 2 → 3 → 4 → 5 → 7、6は3・4の後。
